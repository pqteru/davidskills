先路由，再執行；先文件，再行動。

這份 skill 的核心不是單一演算法，而是一個文件驅動的作業流程。 它把工作拆成有限的 mode，要求每一步只讀必要文件、遵守門檻、留下可審查的證據。

Bootstrap-first router Single active mode Document authority Readiness gate Quality gate

1. 核心心智模型

把它想成「受文件驅動的狀態路由器」，而不是一般的自由對話流程。

狀態不是領域模型，而是作業模式

Planning、Development、Review、Performance、Exception、Update 都是不同的工作模式；每次只能有一個 current mode。

轉移條件來自下一步要做什麼

當下一步變了，就 reroute。這讓流程保持短、乾淨、可重新載入，不把整個聊天脈絡當作唯一記憶。

3. 每個 mode 的角色

Before work
Planning 定義邊界
  • 收斂架構、工作範圍、文件契約
  • 準備 `task.md`、`design.md`、`test.md`、`verification.md`
  • 通過 readiness gate 才能進入開發
Execution
Development 執行批准任務
  • 只做已批准的 active phase
  • 遵守 `task.md` 的順序與 handoff
  • 做完就更新 task / verification
Validation
Quality / Review 驗證與回歸
  • Quality: 先 neutral，再跑 stack-specific checks
  • Review: 只報差異，不默默修正
  • 不符合就回到 Planning 或 Development

4. 文件驅動的規則

1

文件先於行動

這套 skill 的預設不是「先做再整理」，而是先把可執行文件準備好，讓後續 session 不需要重跑整段對話。

2

每個文件有固定責任

`architecture.md` 管邊界，`design.md` 管實作契約，`test.md` 管測試，`task.md` 管 active phase，`verification.md` 管證據。

3

門檻不通過就不能前進

若有 TODO、TBD、未決的路線選擇、或文件互相衝突，就要先修文件；不能靠口頭同意繞過門檻。

4

證據要可審查

成功不是「我覺得完成了」，而是文件、repo state、測試輸出與 verification 能相互對得起來。

5. 何時要 reroute

從 Planning reroute

當你已經有明確 task、要開始實作、或需要驗證回歸，就不能再停留在規劃模式。

從 Development reroute

如果發現架構邊界變了、task 不夠明確、或 readiness gate 失敗，就要回 Planning 而不是硬做。

從 Review reroute

Review 只負責指出差異；如果要修正，就要正式切回 Development。

從 Performance reroute

量測得到的結果若意味著邊界或流程要改，先回 Planning，不要把局部優化擴寫成無約束重構。

6. 一句話總結

這套 skill 的 mindset 不是「一直對話直到自然收斂」，而是「用最小文件集定義當前狀態，通過門檻後執行，最後用證據回寫結果」。
